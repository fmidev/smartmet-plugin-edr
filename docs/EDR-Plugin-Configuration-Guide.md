# Introduction

Name of EDR plugin configuration file is edr.conf.

# Landing page

The landing page (`/edr`), the conformance declaration (`/edr/conformance`) and the API
definition (`/edr/api`) are generated by the plugin. Only the descriptive texts of the
landing page are configured:

```
landing_page:
{
	title       = "FMI EDR Server";
	description = "API for querying meteorological datasets";
	version     = "1.0";    # version of the API definition, default 1.0
	provider:               # optional, any string members
	{
		name = "FMI";
		url  = "https://www.fmi.fi";
	};
	contact:                # optional, any string members
	{
		email = "edr@fmi.fi";
	};
};
```

The title and description are also used in the API definition. The old `api` setting with
JSON templates is obsolete and ignored with a warning.

# API definition and documentation

The plugin generates OpenAPI 3.1 definitions of the EDR API and of each TimeSeries URL from
the configuration and the current metadata, and regenerates them whenever the metadata
changes:

| Resource | Content |
| --- | --- |
| `/edr/api` | OpenAPI definition (`application/vnd.oai.openapi+json;version=3.1`); with `f=html`, or when the client prefers `text/html`, the documentation page |
| `/edr/api/docs` | Documentation page rendered by Swagger UI |
| `/timeseries/api`, `/timeseries/api/docs` | The same for the TimeSeries API (each `timeseries_url`) |
| `/timeseries/api/producers` | The producers of the TimeSeries API with their parameters, areas, times and levels, and a dictionary of parameter descriptions and units; `source=querydata`, `grid` or `observation` selects one source. Used by the data explorer to build queries. |
| `/timeseries/api/producers/{producer}` | One producer with the descriptions of its parameters and its locations (observation stations with their periods); for grid producers also the model runs (`origintime` chooses one) and, per parameter, the level types and levels, forecast types and ensemble members, aggregation and number of times of the run, read from the grid content server; for observation producers with `fmisid` (and optionally `param`, `starttime`, `endtime`) the sensors of the stations, from the observation engine. |

The landing page links the definition (`rel=service-desc`) and the documentation
(`rel=service-doc`). The EDR API and each TimeSeries URL are also listed, with their kinds
(`edr`, `timeseries`), in the API catalog of the server (`/api`), which the documentation
page selector (`/api/docs`) and the data explorer (`/api/explorer`) of the server use; see
the `api_catalog` settings of the server configuration.

The documentation page shows the executed request with its full URL, and as bash (curl),
Python, R and JavaScript snippets. When the request has a time window (`datetime=start/end`,
or `starttime` and `endtime` in the TimeSeries API), the bash, Python, R and JavaScript
"loop" snippets are scripts which repeat the request for consecutive days, weeks, months or
years and save each response to a file; each period ends one second before the next one
starts. The scripts use only curl and GNU date, the Python standard library, base R (4.0 or
newer) and Node.js (18 or newer). JSON and XML responses are shown as a collapsible tree (nodes are
built when opened and long arrays in pages of 200), with the original text view available. The Swagger UI files are served by the plugin from a local directory,
package `smartmet-swagger-ui`, so the documentation does not depend on any public CDN.

```
openapi:
{
	enabled            = true;   # serve the definitions, default true
	ui                 = true;   # serve the documentation pages, default true
	swagger_ui_dir     = "/usr/share/smartmet/swagger-ui";
	expand_collections = true;   # also describe each collection with its exact values
	max_enum           = 1000;   # longer value lists are not listed in the definition
	# Background of the keyword location maps: a Web Mercator tile URL template,
	# normally an OGC API - Tiles layer of the same server. Without it the maps
	# show a longitude/latitude grid.
	map_tiles          = "/tiles/collections/<layer>/tiles/EPSG:3857/{z}/{y}/{x}?f=png";
	map_tile_size      = 256;    # default 256
	map_attribution    = "...";  # shown in the corner of the map
	contact = { name = "FMI"; url = "https://www.fmi.fi"; email = "edr@fmi.fi"; };
	license = { name = "CC BY 4.0"; url = "https://creativecommons.org/licenses/by/4.0/"; };
};
```

With `expand_collections` the definition contains, in addition to the generic
`/collections/{collectionId}/...` paths, the paths of each collection with the collection's
parameter names, output formats, levels, instances and locations as value lists. Clients
such as OGC API Browser use them to validate requests. Value lists longer than `max_enum`
are left out.

On the TimeSeries documentation pages the `keyword` and `inkeyword` parameters have a button
which shows the locations of the given keyword on a map. Moving the mouse over a location
shows its name, ids, coordinates, elevation, region, country and time zone, in the language
of the `lang` parameter. The map can be zoomed with the mouse wheel or the +/− buttons and
moved by dragging. `map_tiles` is either a path on the same server or an http(s) URL; the
origin of a URL is allowed in the Content-Security-Policy of the page.

# AVI engine configuration

Because AVI engine does not provide enough information of its collections they must be introduced in configuration file. AVI engine collection are confgured as follows:

```
avi:
{
	period_length = 30; # 30 days
        collections:
        (
                {
                        name = "METAR";
                        countries = [ "FI" ];
                },
                {
                        name = "TAF";
                        countries = [ "FI" ];
                },
                {
                        name = "SIGMET";
                        icaos = [ "EFIN" ];
                        bbox:
                        {
                                xmin = 19;
                                ymin = 58;
                                xmax = 30;
                                ymax = 70;
                        }
                }
        )
};
```
- period_length parameter tells how old messages can be requested (days, default 30).
- exclude_speci (default true) leaves SPECI messages out of the METAR collection.
- tmppath (default "/var/tmp") is the directory of the temporary files of the IWXXMZIP output format.


Note! if avi-section is not defined no avi collections are visible.


# Supported data queries

Supported data queries are configured as follows:

```
data_queries:
{
	default = ["position","radius","area","cube","locations","trajectory","corridor"];
	override:
	{
		METAR = ["position","radius","area","locations","trajectory","corridor"];
		TAF = ["position","radius","area","locations","trajectory","corridor"];
		SIGMET = ["position","radius","area","locations","trajectory","corridor"];
	};
};
```
The configuration above means that all other collections support 'position','radius','area','cube','locations','trajectory','corridor' queries except METAR,TAF and SIGMET collections which support 'position','radius','area','locations','trajectory','corridor' queries.


# Supported output formats

```
output_formats:
{
    default = ["CoverageJSON","GeoJSON"];
    override:
    {
        METAR = ["CoverageJSON","GeoJSON","IWXXM","TAC"];
        SIGMET = ["CoverageJSON","GeoJSON","IWXXM","TAC"];
        TAF = ["CoverageJSON","GeoJSON","IWXXM","TAC"];
    };
};
```

Currently all collections support CoverageJSON and GeoJSON output formats. Additionally METAR, TAF, SIGMET collections support IWXXM, IWXXMZIP (the IWXXM messages as a zip archive) and TAC output formats.


# Supported locations

In locations section you can define a keyword that is used to get valid locations for each collection. EDR plugin uses this keyword to get locations from GeoEngine. These locations can then be used in location requests for querydata, observation, grid engine location requests. Note! AVI engine is an exception, it provides its own locations and they require no configuration.

```
locations:
{
#	 producer -> keyword
	default = ["synop_fi"];
	override:
	{
		mareograph = ["mareografit"];
	};
};
```
# Supported parameters

You can define supported parameters per producer and rename them at will. For example you can define mareograph parameters as follows:

```
producer_parameters:
{
   opendata_mareograph = ["wlev_pt1s_instant as watlev", "tw_pt1h_avg as twater"];
   mareograph = ["wlev_pt1s_instant as watlev","tw_pt1h_avg as twater"];
};
```

# Disabling engines

If you want to start EDR plugin without avi, observation, grid engine you can use the following settings.

```
aviengine_disabled    = true;
observation_disabled  = true;
gridengine_disabled   = true;
```

# Visible collections

EDR plugin shows all collectiosn provided by engines unless you define visible_collectins settings in configuration file and thus restrict the set of collections.

```
visible_collections:
{
        querydata_engine = ["pal_skandinavia","ecmwf_maailma_pinta"];
        observation_engine = ["road","opendata"];
        # Note! if entry not defined show all collections
        avi_engine = ["*"]; # all collections
        grid_engine = []; # no collections
};
```

# Collection info

Querydata, avi, observation engines do not provide enough information of their collections. In configuration file it is possible to define title, description, keywords for each collection. Note! Grid engine provides title, description information for its collections, so there is no need to configure grid collections.

```
collection_info:
{
	querydata_engine:
	(
		{
			id = "pal_skandinavia";
			title = "Title for collection pal_skandinavia";
			description = "Description for collection pal_skandinavia";
			keywords = ["pal_skandinavia"];
		},
                ...
	),
	avi_engine:
	(
                {
                        id = "METAR";
			title = "METAR message";
			description = "A METAR describes the current weather conditions at a location";
			keywords = ["METAR"];
                },
                ...
        ),
 	observation_engine:
	(
		{
			id = "airquality";
			title = "Title for collection airquality";
			description = "Description for collection airquality";
			keywords = ["airquality"];
		},
                ...
        )
}
```

# Parameter info

Parameter info presented in metadata is gathered from both from engine and configuration file. Configuration file is prioritized: If parameter info is defined in configuration file it is used, otherwise parameter information from engine is used. 

Parameter info in configuration file is defined as follows. Parameter names are matched case-insensitively, so for example `RadiationLW` and `radiationlw` refer to the same parameter; a name may be given only once.

```
parameter_info:
{
	temperature:
	{
		description:
		{
			en = "Air temperature";
			fi = "Ilman lämpötila";
		};
		unit:
		{
			id = "http://codes.wmo.int/common/unit/_degC";
			label:
			{
				en = "Celsius";
				fi = "Celsius";
			};
			symbol:
			{
				value = "°C";
				type = "https://qudt.org/vocab/unit/DEG_C";
			};
		};
	};
	...
};
```

The unit settings follow the CoverageJSON unit object: `label` is required, as is `symbol.value`.
`symbol.type` names the unit vocabulary of the symbol. The MetOcean profile requires QUDT:
`https://qudt.org/vocab/unit/<unit>` with the `qudt:symbol` of the unit as the value, for
example `°C` for `https://qudt.org/vocab/unit/DEG_C`. Without `symbol.type` the symbol is
output as a plain string. The optional `id` identifies the unit itself, for example with a WMO
code registry URI. Parameters without a configured unit use the unit reported by the engine,
if any, as a plain symbol.

# Coordinate reference systems

WGS84 longitude/latitude (OGC:CRS84) is always supported. Additional CRSs for the `crs` query
parameter are listed as EPSG codes:

```
crs = ["EPSG:3067", "EPSG:4326", "EPSG:3857"];
```

# URL, language

```
url           = "/edr";
language      = "fi";
```

Effect of language setting can be seen in EDR metadata title and description fields of collections and parameters. Unfortunately, the language support is currently not comprehensive. Only the observation engine offers translations for parameters. Information about parameters can be added to the configuration file, in which case different language versions are also supported.

# Metadata updates

The metadata of the collections is updated periodically from the engines.

```
metadata_update_interval     = 30;     // seconds, default 30
metadata_updates_disabled    = false;  // true: only the initial update at startup
enable_configuration_polling = false;  // true: reload the plugin when the configuration file changes
```

`pretty = true` makes pretty printed JSON the default; the `pretty` request parameter
overrides it.

# Observation period

Observation database contains observations from very long period. If you want to restrict the period of observations that can be requested via EDR plugin you can define observation_period parameter. 

```
observation_period = 24; // hours
```

# Timeseries interface settings

Since EDR plugin is built on timeseries plugin code base there are some common settings in configuration file, for example precision settings. These are documented in [Using the Timeseries API](Using-the-Timeseries-API.md#plugin-configuration-file).

In addition the plugin can serve the TimeSeries API itself. The feature is optional and is enabled with the timeseries_url setting:

```
timeseries_url = "/timeseries";
```

The value can also be an array of strings, in which case the interface is served at each of the listed paths:

```
timeseries_url = [ "/timeseries", "/pointforecast" ];
```

If the setting is missing, the plugin serves the EDR API only. See [Configuration of the Timeseries Interface](Using-the-Timeseries-API.md#configuration-of-the-timeseries-interface) for details.

Note! Precision defaults can be set separately for the two interfaces: the first entry of precision.enabled is the default of EDR requests, and the first entry of the optional precision.enabled_timeseries is the default of timeseries requests. If precision.enabled_timeseries is not defined, precision.enabled is used for both.
